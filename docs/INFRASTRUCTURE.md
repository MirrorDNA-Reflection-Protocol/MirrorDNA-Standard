## Alerting

External alerts are sent via [ntfy.sh](https://ntfy.sh). Each deployment uses a unique topic ID.

**Alert triggers:**
- Service crash detection
- Endpoint health failures
- Network connectivity loss

**Alert destinations:**
- ntfy.sh mobile push notifications
- Desktop notifications via `osascript`

## Dreaming Service

The `com.mirror.dreaming` service runs nightly at 03:15 for:
1. Dream Engine - Internal log replay and reflection
2. REVELATION - External knowledge synthesis
3. GENESIS - LoRA fine-tuning with OOM protection

**OOM Protection:**
The `self_evolve.py` script includes graceful degradation:
- Attempts training with 4 LoRA layers first
- Falls back to 2 layers if GPU OOM occurs
- Logs failure and continues if all configs exhaust

## Troubleshooting

### Service not running

```bash
# Check if loaded
launchctl list | grep mirrordna

# Reload service
launchctl unload ~/Library/LaunchAgents/ai.mirrordna.SERVICE.plist
launchctl load ~/Library/LaunchAgents/ai.mirrordna.SERVICE.plist

# Check logs
tail -100 ~/.mirrordna/logs/SERVICE_stderr.log
```

### Dreaming crash (OOM)

If the dreaming service crashes with GPU OOM:
1. Check `~/Documents/MirrorDNA-Vault/ActiveMirrorOS/Logs/dreaming_stderr.log`
2. Verify `self_evolve.py` has layer fallback (should use 4, then 2 layers)
3. Ensure T7 Shield external drive is mounted if using external HF cache

### No alerts received

1. Verify ntfy.sh topic: check `~/.mirrordna/scripts/heartbeat.py` for `NTFY_TOPIC`
2. Confirm heartbeat is loaded: `launchctl list ai.mirrordna.heartbeat`
3. Test manually: `python3 ~/.mirrordna/scripts/heartbeat.py`

## Maintenance

### Daily
- Dreaming service runs automatically at 03:15
- Heartbeat sends status every 30 minutes (or immediately on alerts)

### Weekly
- Review `~/.mirrordna/logs/` for anomalies
- Run inventory generation to track system state

### After reboot
- All LaunchAgents auto-load with `RunAtLoad: true`
- Verify with `~/.mirrordna/scripts/verify_infrastructure.sh`
